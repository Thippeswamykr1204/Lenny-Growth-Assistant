# resilience.md — Failure Mode Matrix

Separate file rather than a section inside `architecture.md`: this table
is dense, gets edited independently of architectural decisions, and is the
one doc an operator actually greps during an incident — worth its own
stable path.

Every row is implemented behavior with a pointer to the actual code, not
an aspiration. Where a row was already covered by an earlier tier, this
table references that work rather than rebuilding it.

| Failure mode | Behavior | Code path |
|---|---|---|
| **Ollama unavailable** (connection refused / not running) | `OllamaProvider.stream()` catches `httpx.ConnectError`, yields one `ProviderChunk(error=...)` with a user-safe message ("Is Ollama running?"), never raises. `chat.py` turns that into a typed `error` SSE event. No silent fallback to the cloud provider (locked decision). | `backend/app/providers/ollama_provider.py` (`except httpx.ConnectError`), `backend/app/api/chat.py` (`if stream_error:`) |
| **Cloud API unavailable** (auth failure, rate limit, network error) | `AnthropicProvider.stream()` catches `anthropic.AuthenticationError`, `anthropic.RateLimitError`, and a generic `Exception` fallback, each mapped to a distinct user-safe message; never raises. Same typed SSE error path as Ollama. | `backend/app/providers/cloud_provider.py` |
| **DB unavailable** | Every DB-touching block in `chat.py`'s two streaming generators is wrapped in `try/except SQLAlchemyError`, converting the failure into a `DatabaseUnavailableError` and a typed `error` SSE event instead of an unhandled exception killing the `StreamingResponse` mid-stream. `/api/health`'s `database` dependency reports `status: "unreachable"` distinctly, and the endpoint itself never 500s. | `backend/app/api/chat.py` (`except SQLAlchemyError as exc:` — five call sites across `_event_stream` and `_transform_event_stream`), `backend/app/api/health.py::_check_database` |
| **Retrieval empty** (zero rows in `transcript_chunks`, e.g. ingestion never ran) | `retrieve()` returns a `RetrievalResult` with an empty `chunks` list; `classify()` treats zero chunks clearing the moderate threshold as `"abstain"`. `run_grounded_qa` short-circuits — no LLM call is made — and the user gets the abstention message, not an error. `/api/health`'s `transcript_chunks` dependency separately reports `status: "empty"` so this is diagnosable without hitting `/chat`. | `backend/app/rag/retriever.py::classify`, `backend/app/skills/grounded_qa.py` (abstention path), `backend/app/api/health.py::_check_transcript_chunks_table` |
| **Retrieval low confidence** *(already handled, Tier 3 — referenced, not rebuilt)* | Confidence gating (`answer` / `qualified` / `abstain`) based on configurable similarity thresholds. A single low-confidence chunk still answers, hedged; genuinely no evidence abstains before ever calling a provider. | `backend/app/rag/retriever.py::classify`, `backend/app/skills/grounded_qa.py` |
| **LLM timeout** | Both providers catch their SDK/HTTP-level timeout exception (`httpx.TimeoutException` for Ollama, `anthropic.APITimeoutError` for Anthropic) and yield a typed error chunk with a distinct "took too long" message. Timeouts are now settings-driven per provider (`OLLAMA_TIMEOUT_SECONDS`, `ANTHROPIC_TIMEOUT_SECONDS`), not a shared hardcoded value. **Partial-response decision:** tokens already streamed to the client before the timeout are shown to the user but **discarded, not persisted** as a truncated assistant message — see the in-code rationale comment for why (a silently-incomplete message replayed as conversation history on the next turn is worse than an obviously-missing one). A retry re-runs retrieval + generation from scratch. | `backend/app/providers/ollama_provider.py`, `backend/app/providers/cloud_provider.py`, `backend/app/api/chat.py` (`if stream_error:` block, comment explains the persistence decision) |
| **Invalid/blocked artifact** *(already handled, Tier 4 — referenced, not rebuilt)* | HTML artifacts pass through `sanitize_html()` before persistence; a blocked payload is still persisted and still emitted as an `artifact` SSE event (never silently dropped), with `security_status: "blocked"` rendered as a visible banner in `ArtifactViewer.tsx`, not a blank pane. | `backend/app/skills/artifact_generator.py::sanitize_html`, `frontend/src/components/Artifact/ArtifactViewer.tsx` |
| **Malformed model output** (HTML generation returns empty/unusable content) | `generate_html_artifact()` returning `None`/empty or a `ProviderError` is checked explicitly in `chat.py` before sanitization is even attempted; the request fails with a typed `error` SSE event ("Couldn't generate the artifact right now") rather than persisting an empty or partially-formed artifact. | `backend/app/api/chat.py::_transform_event_stream` (`if error is not None or not raw_html:`) |
| **Empty user prompt** | Validated at the endpoint, before retrieval or any provider call: `chat_stream()` returns HTTP 422 on a blank/whitespace-only message. Pre-existing from an earlier tier — confirmed still in place. | `backend/app/api/chat.py::chat_stream` (`if not req.message.strip():`) |
| **Oversized prompt** *(gap found and fixed this tier)* | No prior upper bound existed. `chat_stream()` now rejects messages longer than `MAX_PROMPT_CHARS` (default 8000) with HTTP 422, before retrieval or any provider call — same validation tier as the empty-message check, so a pathological payload never reaches a provider's own token/cost limits unvalidated. | `backend/app/api/chat.py::chat_stream`, `backend/app/core/config.py::Settings.max_prompt_chars` |
| **Missing required API key at startup** | `validate_config(settings)` (single function, called from both places below) flags `default_llm_provider=anthropic` with no `ANTHROPIC_API_KEY` as a `ConfigurationError`. `main.py`'s startup handler calls it and raises, refusing to boot, with a clear message in the logs — instead of booting successfully and failing confusingly on the first chat request. `ANTHROPIC_API_KEY` is explicitly **not** required when the default provider is `ollama` (regression-guarded by tests). | `backend/app/core/config.py::validate_config`, `backend/app/main.py::on_startup` |
| **Misconfiguration visible at runtime, not just in startup logs** *(new this tier)* | `/api/health` calls the same `validate_config()` and reports a `configuration` dependency with `status: "misconfigured"` when applicable; `overall` becomes `"misconfigured"` — a state distinct from `"degraded"` (a live dependency being down) or `"ok"`, because the remediation is different (fix `.env` / redeploy vs. wait for a dependency to come back). | `backend/app/api/health.py::_check_configuration` |
| **DB connection pool exhausted / slow to hand out a connection** *(new this tier)* | `db_pool_timeout_seconds` (default 5s, settings-driven) bounds how long a request waits for a pooled connection before SQLAlchemy raises, which is caught by the same `SQLAlchemyError` handling as the "DB unavailable" row above — a saturated pool degrades the same way a fully-down DB does, rather than queuing requests indefinitely. | `backend/app/db/session.py` (`pool_timeout=settings.db_pool_timeout_seconds`) |

## Verification discipline

Each row above is either:
- **Live-verified**: actually triggered (stopped a container, forced an exception via monkeypatch, ran the request) and observed the described behavior, or
- **Statically reasoned**: read the code path and confirmed it matches the description, without triggering the actual failure in a running system.

See the verification report in the final Tier 5 summary for which rows got which treatment this turn — that discipline is restated per-tier rather than assumed to carry over.
